Git worktree — jedno repo, kilka biurek

Jak trzymać kilka gałęzi rozpakowanych naraz, po co to komu przy pracy z kilkoma agentami — i co takiej równoległości i tak nie da się zrównoleglić.

Problem: katalog roboczy jest jeden

Zwykłe repozytorium ma jeden katalog z plikami. git checkout nie kopiuje niczego obok — przepisuje to samo miejsce na dysku. Przełączenie gałęzi znaczy więc, że pliki, które przed chwilą czytałeś, zmieniają się pod ręką: edytor pokazuje inną wersję, serwer deweloperski przeładowuje inny kod, a niezacommitowane zmiany albo jadą z tobą na drugą gałąź, albo blokują przełączenie.

Przy jednym zadaniu naraz to nie przeszkadza. Przeszkadza, gdy zadania są dwa: pilna poprawka w trakcie dużej przebudowy, przegląd cudzej gałęzi bez porzucania własnej, dwa agenty pracujące jednocześnie. Klasyczne obejścia to git stash (kruche — kolejka schowków jest wspólna i łatwo w niej zgubić rachubę) albo drugi git clone (działa, ale to osobne repozytorium: własna kopia całej historii, własne remote, własne gałęzie, które trzeba ręcznie synchronizować).

Worktree to trzecia droga: jedno repozytorium, kilka katalogów roboczych. Historia, gałęzie i remote pozostają wspólne — mnożą się tylko rozpakowane pliki.

Cztery polecenia, które wystarczą

# nowa gałąź + nowy katalog obok repozytorium
git worktree add -b docs/git-worktree ../TradingCenter-article main

# istniejąca gałąź (np. czyjś PR do przejrzenia)
git worktree add ../TradingCenter-review feat/terminal-market-data-auth

# co w tej chwili gdzie stoi
git worktree list

# sprzątanie po skończonej robocie
git worktree remove ../TradingCenter-review

Ostatni argument add to punkt startowy — bez niego nowa gałąź odbija od bieżącego HEAD, co przy pracy na gałęzi tematycznej rzadko jest tym, o co chodziło. Warto pisać main jawnie.

Nazwa katalogu jest dowolna, ale konwencja tego repozytorium to katalog siostrzany, nazwany TradingCenter-<temat>. Katalog wewnątrz repozytorium też zadziała, tylko trzeba go potem dopisać do .gitignore, żeby git nie zaczął go traktować jak zwykłe pliki projektu.

Jedna gałąź stoi w jednym miejscu

Git nie pozwoli wypakować tej samej gałęzi w dwóch worktree naraz:

fatal: 'main' is already checked out at '/Users/…/TradingCenter'

To nie ograniczenie do obejścia — to właśnie zabezpieczenie, dla którego całość działa. Dwa katalogi commitujące na tę samą gałąź nadpisywałyby sobie wskaźnik gałęzi i każdy widziałby cudze commity jako „zniknięte” zmiany. Stąd naturalna zasada: jeden worktree, jedna gałąź, jedno zadanie.

Co jest wspólne, a co własne

To jest cała mechanika worktree i jedyna rzecz, którą warto zapamiętać dosłownie. Plik .git w dodatkowym worktree nie jest katalogiem, tylko jedną linijką wskazującą z powrotem na .git/worktrees/<nazwa> w repozytorium głównym. Wszystko, co siedzi w magazynie obiektów, jest jedno na wszystkich; wszystko, co opisuje stan pracy, jest osobne.

RzeczZasięgCo z tego wynika
commity, tagi, historia wspólne commit w jednym worktree widać z pozostałych od razu, bez push i fetch
gałęzie i remote wspólne jeden git fetch aktualizuje wszystkie; jedna lista gałęzi dla całości
git stash wspólne schowek zrobiony tu widać tam — najczęstsza pułapka, bo intuicja podpowiada odwrotnie
.git/config, hooki wspólne hook require-review.sh działa jednakowo w każdym worktree
pliki robocze, HEAD, index własne istota rzeczy: edycje i staging jednego worktree są niewidoczne dla drugiego
stan rebase, merge, bisect własne przerwany rebase nie blokuje pracy w sąsiednim katalogu
pliki nieśledzone i ignorowane własne .env, .venv, node_modules — nowy worktree dostaje pusto i trzeba je odtworzyć

Ostatni wiersz to jedyny realny koszt wejścia. Świeży worktree ma pliki z gita i nic poza tym, więc zanim cokolwiek uruchomisz:

# pliki środowiskowe — nie ma ich w repozytorium, więc kopiujesz z sąsiada
cp ../TradingCenter/modules/capital-gateway/.env modules/capital-gateway/.env
cp ../TradingCenter/modules/market-data/.env      modules/market-data/.env

# zależności — osobne dla każdego katalogu
cd modules/market-data && uv sync
cd ../../modules/terminal && pnpm install

Kilka agentów, kilka worktree

Agent pracuje tak samo jak człowiek: czyta pliki, zapisuje pliki, uruchamia testy. Dwa agenty w jednym katalogu roboczym to dwie osoby piszące w jednym zeszycie — jeden zmienia plik między odczytem a zapisem drugiego, testy wywracają się na cudzej niedokończonej edycji, a git checkout zrobiony przez jednego wyciąga drugiemu pliki spod palców.

Worktree usuwa całą tę klasę problemów jednym ruchem: każdy agent dostaje własny katalog i własną gałąź. Nie muszą się umawiać, kto teraz pisze, bo fizycznie nie dotykają tych samych plików. Praca spotyka się dopiero tam, gdzie ma się spotykać — w historii gita, przez pull requesty do main.

Konflikty nie znikają, ale zmieniają charakter: zamiast rozjeżdżonego stanu na dysku, który trudno nawet zauważyć, dostajesz zwykły konflikt merge’a — widoczny, opisany, rozwiązywany narzędziem, które do tego służy.

Praktyczny podział

Jedno zadanie na worktree, nazwa katalogu z tematu zadania, gałąź od main. Po scaleniu PR-a katalog się usuwa. Cztery równoległe wątki to cztery katalogi obok siebie — git worktree list jest wtedy najkrótszym opisem tego, co się w projekcie dzieje.

Czego worktree nie rozdziela

I tu jest granica, o którą naprawdę się zawadza. Git rozdziela pliki. Nie rozdziela niczego poza sobą — a uruchomiony projekt to nie tylko pliki. Porty TCP, kontener bazy, sesja u brokera: te zasoby są jedne na całą maszynę, niezależnie od tego, w ilu katalogach stoi kod.

Trzy kolizje w tym repozytorium
  • Porty są stałe — 8010 gateway, 8020 market-data, 5173 terminal. Drugi ./scripts/dev.sh nie wystartuje albo, gorzej, podepnie się pod cudzy proces.
  • Baza to jeden kontener z compose.yaml, jeden projekt Dockera i jeden wolumen. Migracja puszczona w jednym worktree zmienia schemat, który widzą wszystkie pozostałe.
  • Sesja demo capital.com jest jedna — każde nowe logowanie unieważnia poprzednie (capital_gateway/client.py). Dwa gateway’e na tym samym koncie wzajemnie się wylogowują, a objaw to losowe 401 w obu.

Wniosek: równolegle można pisać kod, czytać, planować i uruchamiać testy jednostkowe. Testy -m db są bezpieczne, bo testcontainers podnosi własny kontener na losowym porcie. Ale pełny stack i migracje — jeden agent naraz.

Sprzątanie i typowe zgrzyty

git worktree remove kasuje katalog, ale nie kasuje gałęzi — bo gałąź jest wspólną własnością repozytorium, nie tego katalogu. Po scaleniu PR-a usuwa się ją osobno.

git worktree remove ../TradingCenter-article
git branch -d docs/git-worktree      # osobno, dopiero po merge’u
ObjawPrzyczyna i co zrobić
is already checked out at … Ta gałąź stoi w innym worktree. git worktree list pokaże gdzie. Albo pracuj tam, albo zrób nową gałąź.
contains modified or untracked files remove broni się przed skasowaniem niezacommitowanej pracy. Zacommituj — albo --force, jeśli świadomie wyrzucasz.
worktree na liście, katalogu nie ma Katalog skasowany ręcznie, wpis został. git worktree prune czyści listę.
testy padają na brak .env albo zależności Świeży worktree nie dziedziczy plików ignorowanych. Skopiuj .env, uruchom uv sync / pnpm install.
„gdzie mój stash?” Tam gdzie zawsze — schowki są wspólne dla całego repozytorium. git stash list działa z każdego worktree.
Worktree kontra git clone — kiedy który

Worktree, gdy chodzi o równoległą pracę nad tym samym projektem: jedna historia, jeden fetch, commity od razu widoczne wszędzie, kilkaset megabajtów historii trzymane raz.

Osobny clone, gdy potrzebna jest prawdziwa izolacja: eksperyment, który może zepsuć repozytorium, praca na cudzym forku z innymi remote, albo test świeżego rozpakowania projektu od zera. Za tę izolację płaci się ręczną synchronizacją i duplikatem historii.

Ściągawka

git worktree add -b <gałąź> <ścieżka> main   # nowa gałąź w nowym katalogu
git worktree add <ścieżka> <gałąź>            # istniejąca gałąź
git worktree list                             # co gdzie stoi
git worktree remove <ścieżka>                 # usuń katalog (gałąź zostaje)
git worktree prune                            # posprzątaj wpisy po ręcznie skasowanych
git worktree lock <ścieżka>                   # chroń przed prune (dysk zewnętrzny)
