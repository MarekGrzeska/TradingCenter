teams — testy lokalne

Scenariusze do przejścia ręką na działającym stosie, zanim gałąź feat/teams-module pójdzie do main. To, czego nie sprawdzi żaden test automatyczny: konfiguracja, prawdziwy model po drugiej stronie, prawdziwe pieniądze i to, co widać na ekranie.

Dotyczy: modules/teams (port 8050), modules/terminal (zakładka Teams)
Zmiana: openspec/changes/add-teams-module, zadanie 12.2
Opis modułu i mapa architektury: docs/teams-modul-i-architektura.html

Przeczytaj to przed pierwszym przebiegiem

Przebieg zespołu wydaje prawdziwe pieniądze na prawdziwym kluczu OpenAI — i to nie jedno wywołanie, tylko tyle, ilu agentów razy do sześciu rund każdy. Klucz jest osobny od agent (teams-openai-api-key) właśnie po to, żeby ten koszt było widać na własnej linii rachunku.

Każda definicja z tego dokumentu ma ustawione limits. Nie usuwaj ich „na chwilę". Zacznij od najtańszego modelu z GET /models i od dwóch agentów, nie od pięciu.

Zanim zaczniesz

Cztery rzeczy, które psują przebieg, zanim się zacznie
  • Docker musi być wstały. Baza deweloperska to kontener z compose.yaml, 127.0.0.1:55432. teams to trzecia baza logiczna w tym samym kontenerze; skrypty dev.* zakładają rolę i bazę same, jeśli którejś nie ma.
  • .env jest per moduł i nie jest w gicie. Skopiuj z modules/teams/.env.example i wypełnij OPENAI_API_KEY oraz MODELS. Bez klucza moduł nie wstanie — i to jest zamierzone.
  • Identyfikatory modeli z .env.example są przykładowe. Wpisz te, które twoje konto OpenAI faktycznie serwuje. Nazwa, której konto nie zna, przechodzi konfigurację bez słowa i wywala się na pierwszym wywołaniu pierwszego przebiegu.
  • Jeden stos naraz. Porty są stałe, kontener bazy jeden, a budżet zapytań capital.com liczy się na konto — także między git worktree.

Ręczny przebieg ma sens dopiero, gdy to jest zielone. Komendy z katalogu modułu; w repozytorium nie ma niczego, co zbuduje albo przetestuje wszystko naraz.

Kolejność jest wymuszona i każdy krok czeka, aż poprzedni odpowie: migracje → capital-gateway (8010) → market-data (8020) → market-mcp (8040) → agent (8030) → teams (8050) → terminal (5173).

Wspólny nagłówek dla scenariuszy HTTP

Lokalnie nikt nie stoi przed modułem, więc REQUIRE_AUTHENTICATED_PRINCIPAL=false nadaje każdemu żądaniu tożsamość anonymous. Cudzą tożsamość udaje się nagłówkiem — tak samo, jak zrobiłby to Easy Auth.

$t   = "http://127.0.0.1:8050"
$ja  = @{}                                        # anonymous
$ktos= @{ "X-MS-CLIENT-PRINCIPAL-ID" = "ktos-inny" }

function Get-Json($url, $h = $ja) { Invoke-RestMethod -Uri $url -Headers $h }
function Post-Json($url, $body, $h = $ja) {
  Invoke-RestMethod -Method Post -Uri $url -Headers $h `
    -ContentType application/json -Body ($body | ConvertTo-Json -Depth 8)
}

A. Start i konfiguracja

TC-01 Moduł migruje się sam i dopiero potem odpowiada

Kroki
Skasuj bazę logiczną (DROP DATABASE teams w kontenerze) i uruchom stos od nowa. Potem: Get-Json "$t/health".
Oczekiwane
Skrypt dev.* zakłada rolę i bazę. Moduł wykonuje migracje we własnym lifespan, pod advisory lockiem o kluczu 8050, zanim zacznie odpowiadać — więc sam fakt, że /health odpowiada, jest dowodem, że schemat jest na głowie. Żadnego kroku operatora między jednym a drugim.

TC-06 Zespół powstaje razem z pierwszą rewizją

Kroki
Podstaw pod $tani i $drogi identyfikatory z GET /models:
$def = @{
  agents = @(
    @{ key="zbieracz"; role="Zbiera fakty"; prompt="Wypisz trzy fakty o rynku US100 z dostepnych danych.";
       model_id=$tani;  tools=@() },
    @{ key="sedzia";   role="Decyduje";     prompt="Na podstawie faktow poprzednika napisz jedno zdanie rekomendacji.";
       model_id=$drogi; tools=@() }
  )
  edges  = @( @{ from="zbieracz"; to="sedzia" } )
  limits = @{ run_limit="0.05"; daily_limit="0.20" }
}
$zespol = Post-Json "$t/teams" @{ name="Proba 1"; description="scenariusz TC-06"; definition=$def }
$zespol
Oczekiwane
201, latest_revision = 1. GET /teams pokazuje wpis; GET /teams/{id}/revisions/latest oddaje definicję dokładnie taką, jaka poszła — łącznie z limits jako łańcuchami.
Podstawa
zadania 4.2, 4.4

TC-07 Cztery odmowy zapisu, każda nazywająca winowajcę

Kroki

TC-16 Agent widzi poprzedników, a nie całą historię

Kroki

TC-17 Strumień postępu: najpierw migawka, potem zdarzenia

Kroki

Przywróć w .env: RUN_TIMEOUT_SECONDS=900, oryginalne stawki w MODELS, MARKET_MCP_URL. Bazę testową kasuje się razem z wolumenem kontenera — ale nie musisz: katalog zespołów jest mały, to nie jest tabela świec.

Czego ten przebieg nie sprawdza

Uczciwie, żeby nie było potem niespodzianki

Monitor przebiegu w terminalu (9.9, 9.10) i start z katalogu (9.4) nie istnieją, więc scenariusze D idą przez HTTP. Gdy grupa 9 się domknie, TC-15, TC-17 i TC-18 zyskają wariant „to samo, ale z canvasu".

GET /tools i wybierak narzędzi (9.7) — TC-14 sprawdza dziś stan przejściowy, a nie docelowy.

Azure. Kod infrastruktury jest napisany i terraform validate przechodzi, ale apply jest robotą operatora i nie został wykonany — w chmurze nie stoi jeszcze nic. Wdrożenie ma własną kolejność (-target na App Service, pełny apply, sekret w Key Vault, rola w bazie i grant-schema-ownership.sql) opisaną w sekcji „Deploy" pliku modules/teams/README.md; jedna rzecz jest tam jawnie oznaczona jako do sprawdzenia — dokładne wywołanie zakładające rolę Entra w bazie.

Zachowanie przy dwóch instancjach. Rejestr przebiegów siedzi w pamięci procesu, a plan ma dokładnie jednego workera. Drugi worker nie jest testowany, bo nie jest wspieraną konfiguracją — odpowiedzią na brak pamięci jest większy SKU, nigdy drugi worker.

Dokument roboczy do zadania 12.2 zmiany add-teams-module. Po przejściu scenariuszy wynik idzie do review.md; ten plik zostaje jako zapis, co i jak było sprawdzone ręką. Prawdą o systemie są specyfikacje teams-* i terminal-teams.
