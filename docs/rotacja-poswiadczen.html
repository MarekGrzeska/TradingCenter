Rotacja poświadczeń

Co w tej platformie wygasa samo, czego się nie da zapomnieć bezkarnie, i co zrobić, gdy termin minie.

Dotyczy stanu po zmianie provision-azure-platform
Powiązane: docs/dbeaver-azure-connection.html, infra/key-vault.tf, infra/entra.tf

Zasada

Większość tej platformy nie ma czego rotować, i to jest wybór, nie przypadek. Baza nie zna żadnego hasła — każde połączenie bierze świeży token Entra w momencie nawiązywania, więc nie ma tam poświadczenia, które mogłoby wyciec albo wygasnąć. Wdrożenia nie trzymają sekretu do Azure — GitHub Actions wymienia własny token OIDC na token Azure przy każdym uruchomieniu. Klucze dostępu do konta magazynu stanu są wyłączone na poziomie konta, więc te, które siedzą w zacommitowanym pliku stanu, są trwale martwe.

Zostaje krótka lista rzeczy, które naprawdę wygasają. Ta strona jest o nich.

Dwie daty warte zapisania w kalendarzu

Oba sekrety aplikacji Entra wygasają 9 sierpnia 2027. Terraform ich nie odnowi sam — ma na end_date jawne ignore_changes, bo bez tego każdy plan chciałby je rotować (timestamp() nigdy nie zwraca dwa razy tej samej wartości). Odnowienie jest ręczne i opisane niżej.

Czego rotować nie trzeba, i dlaczego
  • Hasło do bazy — nie istnieje. password_auth_enabled = false na serwerze; aplikacja i twój lokalny proces biorą token Entra przy każdym nowym połączeniu, a biblioteka odnawia go sama.
  • Sekret do Azure w GitHubie — nie istnieje. Wdrożenia idą przez federację OIDC, a poświadczenia federowane nie mają daty ważności.
  • Klucze konta magazynu stanu — wyłączone (shared_access_key_enabled = false). Terraform sięga do stanu tożsamością Entra.

Jak odnowić

Token do GHCR

App Service musi mieć czym pobrać obraz z GHCR-a, bo repozytorium jest prywatne. Token to zwykły PAT z jednym zakresem — read:packages. Nie nadawaj mu więcej; nic więcej nie robi.

  1. Nowy token: github.com/settings/tokens → Generate new token (classic) → zaznacz wyłącznie read:packages.
  2. Wstaw go do sejfu i zrestartuj obie aplikacje — restart jest po to, żeby nie czekać, aż App Service odświeży referencję do Key Vaulta sam z siebie:
az keyvault secret set --vault-name kv-tradingctr-58hw \
  --name ghcr-pull-token --value <NOWY_TOKEN>

az webapp restart --name app-tradingcenter-gateway     --resource-group rg-tradingcenter
az webapp restart --name app-tradingcenter-market-data --resource-group rg-tradingcenter

Sprawdzenie, że zadziałało — obie powinny odpowiedzieć czymś innym niż 503:

curl -o /dev/null -w '%{http_code}\n' https://app-tradingcenter-gateway.azurewebsites.net/
Co zobaczysz, gdy token wygaśnie

Strona odpowiada 503, a wdrożenie w GitHub Actions jest zielone — bo workflow zbudował obraz, wypchnął go i przypisał do App Service, i to wszystko się udało. Nie udało się dopiero pobranie obrazu przez Azure, a to dzieje się już poza pipeline'em. Log kontenera:

az webapp log download --name app-tradingcenter-market-data \
  --resource-group rg-tradingcenter --log-file logi.zip

W środku LogFiles/*_docker.log — szukaj ImagePullUnauthorizedFailure.

Sekrety aplikacji Entra

Terraform zna te zasoby, ale celowo nie pilnuje ich daty ważności. Odnowienie to wymuszone odtworzenie — jednego albo drugiego, w katalogu infra/:

terraform apply -replace=azuread_application_password.market_data_easy_auth
terraform apply -replace=azuread_application_password.market_data_dev

Easy Auth nie wymaga nic więcej: nowa wartość wchodzi do ustawień market-data tym samym apply, bo ustawienie czyta ją wprost z zasobu.

Tożsamość deweloperska tak — jej sekret żyje też w twoim lokalnym pliku, a tam Terraform nie sięga:

terraform output -raw market_data_dev_client_secret

Wynik wklej do modules/market-data/.env jako AZURE_CLIENT_SECRET.

Token wdrożeniowy Static Web Apps

Jedyny sekret Azure trzymany po stronie GitHuba, i jedyny dlatego, że Azure/static-web-apps-deploy nie ma ścieżki OIDC. Jeśli Static Web App kiedykolwiek powstanie na nowo, token trzeba przenieść:

gh secret set AZURE_STATIC_WEB_APPS_API_TOKEN \
  --body "$(terraform output -raw terminal_api_key)"

Klucz między modułami

gateway-api-key to jedna wartość w trzech miejscach: w sejfie (skąd czytają obie wdrożone usługi) oraz w dwóch lokalnych plikach .env. Rotacja oznacza podmianę wszędzie, inaczej market-data zacznie dostawać 401 od gatewaya.

az keyvault secret set --vault-name kv-tradingctr-58hw \
  --name gateway-api-key --value <NOWY_KLUCZ>

az webapp restart --name app-tradingcenter-gateway     --resource-group rg-tradingcenter
az webapp restart --name app-tradingcenter-market-data --resource-group rg-tradingcenter

Potem to samo w modules/capital-gateway/.env i modules/market-data/.env — obie strony muszą trzymać identyczną wartość.

Rzecz pokrewna: migracje bazy produkcyjnej

Nie jest to rotacja, ale mieszka w tej samej szufladzie „rzeczy, które robi się rzadko i za każdym razem od zera". Baza market_data należy do tożsamości zarządzanej market-data, a jej tokenu nie da się zdobyć spoza App Service — istnieje wyłącznie w procesie kontenera. Z laptopa dostanie się tam tylko twoje konto administratora.

Gdyby migracje puścić po prostu jako administrator, właścicielem tabel zostałbyś ty, a aplikacja potrzebowałaby osobnych GRANT-ów przy każdej nowej tabeli. Na market_data_dev tak nie jest — tam właścicielem jest ta sama rola, która bazy używa. Poniższe trzy kroki utrzymują tę samą własność na produkcji.

1. Niech twoja sesja działa jako rola aplikacji

Jednorazowe GRANT członkostwa, a potem ustawienie zawężone do tej jednej bazy — sesje przeciw market_data_dev zostają nietknięte:

GRANT "app-tradingcenter-market-data" TO "<twój UPN>";
ALTER ROLE "<twój UPN>" IN DATABASE market_data
  SET role = "app-tradingcenter-market-data";

2. Puść migracje

DefaultAzureCredential czyta AZURE_* wprost ze zmiennych procesu, więc lokalny .env z poświadczeniami dewelopera musi zniknąć z pola widzenia — inaczej alembic uwierzytelni się jako Service Principal deweloperski, który do market_data nie ma CONNECT. Puste stringi nie wystarczą: biblioteka wywraca się na nich osobno.

cd modules/market-data
mv .env .env.tmp-hidden

env -u AZURE_CLIENT_ID -u AZURE_CLIENT_SECRET -u AZURE_TENANT_ID \
  DATABASE_URL="postgresql://psql-tradingcenter.postgres.database.azure.com:5432/market_data?sslmode=require" \
  DATABASE_USER="<twój UPN>" \
  GATEWAY_API_KEY="not-used-by-migrations" \
  uv run alembic upgrade head

mv .env.tmp-hidden .env

3. Cofnij ustawienie i sprawdź własność

SET ROLE NONE;   -- nie RESET ROLE: ten wraca do wartości domyślnej,
                 -- czyli dokładnie do tego, co próbujesz cofnąć
ALTER ROLE "<twój UPN>" IN DATABASE market_data RESET role;

select tablename, tableowner from pg_tables where schemaname = 'public';
Objaw, gdy o tym zapomnisz

Wdrożenie w GitHub Actions jest zielone, obraz się pobiera, kontener startuje — i wychodzi z kodem 3 po kilkudziesięciu sekundach. W logu startowym: asyncpg.exceptions.UndefinedTableError: relation "…" does not exist. Tożsamość zarządzana połączyła się z bazą poprawnie; po prostu nie ma tam jeszcze tabel.

Rzecz pokrewna: twój adres IP

Nie jest poświadczeniem, ale psuje się tak samo cicho. Firewall bazy przepuszcza dokładnie jeden adres deweloperski, a dostawca internetu potrafi go zmienić bez uprzedzenia. Objaw: lokalny market-data i DBeaver nagle nie łączą się z bazą, mimo że nic nie zmieniałeś.

curl ifconfig.me

Nowy adres wpisz w dwóch miejscach — infra/terraform.tfvars (lokalnie, plik jest gitignorowany) i w zmiennej repozytorium, z której korzysta terraform plan w CI:

gh variable set TF_VAR_DEVELOPER_IP_ADDRESS --body <NOWY_ADRES>

Następnie terraform apply w infra/. Bez zmiany w obu miejscach naraz plan w CI będzie pokazywał różnicę względem tego, co masz lokalnie.

Uwaga na koniec

terraform apply dla tej platformy uruchamiasz ty, lokalnie — nie ma go w CI i nie jest to niedopatrzenie. Ten root zarządza obiektami katalogu Entra, a nadanie pipeline'owi prawa zapisu do katalogu byłoby większym uprawnieniem niż cokolwiek innego w tym projekcie. CI robi wyłącznie plan na pull requestach. Powód jest zapisany w nagłówku .github/workflows/terraform.yml.

Gdy coś tu przestanie być prawdą — zmieni się nazwa sejfu, dojdzie czwarty sekret, zniknie PAT na rzecz Azure Container Registry — popraw ten plik przy tej samej zmianie, nie później.
