Plan wdrożenia na VPS

Deploye, sekrety, autoryzacja i to, co faktycznie jest trudniejsze niż w chmurze. Prostym językiem.

Stan na 2026-08-07 · zakłada VPS z Dockerem i repozytorium MarekGrzeska/TradingCenter

Wniosek na wstępie

Z czterech rzeczy, dla których chciałeś Azure — łatwe deploye, integracja z GitHubem, sekrety w vaulcie, autoryzacja — trzy pierwsze załatwiasz narzędziami, które już masz, w większości za darmo. Autoryzacja wychodzi nawet lepiej niż w Azure.

Realnie trudniejsza jest jedna rzecz: to, że jesteś właścicielem systemu operacyjnego i kopii zapasowych. I to jest cała różnica, za którą płaciłbyś w chmurze.

1. Cztery obawy, po kolei

✓ rozwiązane

„Chciałem łatwych deployów"

GitHub Actions wdraża na VPS równie łatwo jak do Azure. Robisz git push, Actions buduje obrazy, wysyła je do rejestru GitHuba, a potem łączy się z VPS-em po SSH i mówi „pobierz nową wersję i zrestartuj". Całość to około 40 linii pliku YAML, pokazanego w sekcji 3.

Wdrożenie do Azure App Service to też GitHub Actions i też plik YAML podobnej długości. Przewaga chmury jest tu praktycznie żadna — po prostu w jednym przypadku ostatnim krokiem jest „wyślij do Azure", a w drugim „wejdź po SSH i pociągnij obraz".

✓ rozwiązane

„Chciałem wygodnego połączenia z GitHubem"

Rejestr obrazów GitHuba (ghcr.io) jest wbudowany w twoje repozytorium. Nie zakładasz konta, nie konfigurujesz dostępu — Actions ma automatyczny token do wypychania obrazów. VPS pobiera je tym samym mechanizmem.

W praktyce jest to bliżej GitHuba niż Azure, bo wszystko dzieje się w obrębie jednego dostawcy.

Uwaga na limit: prywatne obrazy liczą się do darmowego pakietu GitHub Packages, który na planie darmowym jest niewielki. Rozwiązanie: trzymaj tylko tag latest i sprzątaj stare wersje, albo ustaw obrazy jako publiczne — pod warunkiem, że nie wbudowujesz w nie żadnych sekretów, czego i tak nie wolno robić.

✓ rozwiązane

„Chciałem trzymać sekrety w vaulcie"

GitHub Secrets to jest vault — szyfrowany, z kontrolą dostępu, wbudowany w repozytorium i darmowy. Wpisujesz tam klucz API do capital.com i hasło do bazy, a podczas wdrożenia Actions zapisuje je na VPS-ie do pliku .env z uprawnieniami tylko dla właściciela.

Azure Key Vault daje ponadto dziennik dostępu i mechanizmy rotacji. Przy jednym operatorze i jednym zestawie poświadczeń nie kupujesz tym nic realnego, a płacisz i dokładasz zależność.

Gdybyś chciał czegoś ładniejszego: SOPS + age pozwala trzymać zaszyfrowane sekrety w repozytorium, a VPS odszyfrowuje je swoim kluczem. Zyskujesz historię zmian sekretów w gicie. To rozwinięcie na później, nie warunek startu.

✓ rozwiązane — i lepiej niż w Azure

„No i jeszcze autoryzacja?"

Cloudflare Access stawia przed twoją aplikacją stronę logowania — Google, GitHub albo kod jednorazowy na e-mail — i przepuszcza wyłącznie osoby z listy. Nie piszesz do tego ani linijki kodu. Darmowe do 50 użytkowników, na stałe.

Do tego dokładasz Cloudflare Tunnel: VPS nie ma żadnego otwartego portu przychodzącego, bo to tunel dzwoni na zewnątrz. Wchodzisz z dowolnej przeglądarki na świecie, bez klienta VPN.

Odpowiednik w Azure to Entra ID z App Service Easy Auth — działa dobrze, ale jest zaprojektowany dla organizacji z wieloma użytkownikami i wymaga, żeby aplikacja stała w Azure.

3. Jak wygląda wdrożenie

Robisz git push na gałąź main. Dalej dzieje się to samo:

name: deploy

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: modules/capital-gateway
          push: true
          tags: ghcr.io/marekgrzeska/capital-gateway:latest

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.VPS_HOST }}
          username: deploy
          key: ${{ secrets.VPS_SSH_KEY }}
          script: |
            cd /srv/tradingcenter
            docker compose pull
            docker compose up -d
            docker image prune -f

To wszystko. VPS_HOST i VPS_SSH_KEY siedzą w GitHub Secrets, więc nigdzie w repozytorium nie ma adresu ani klucza.

Dlaczego budować w Actions, a nie na VPS-ie

Kuszące jest zrobić po prostu git pull && docker compose up -d --build na serwerze. Nie rób tego: budowanie frontendu potrafi zjeść 1–2 GB pamięci, a robi to na tej samej maszynie, na której akurat pracuje Postgres i leci ingest. Na małym VPS-ie kończy się to ubiciem procesu przez system i dziurą w danych.

Budowanie w Actions jest darmowe i dzieje się na cudzej maszynie. VPS tylko pobiera gotowy obraz.

4. Co naprawdę jest trudniejsze

Teraz uczciwie — nie wszystko wychodzi na zero.

✗ realny koszt

Kopie zapasowe są twoje

To jest ta jedna rzecz, za którą naprawdę płaci się w chmurze. Zarządzana baza robi kopie sama i sama pilnuje, żeby dało się z nich odtworzyć.

Dlaczego to tu boli szczególnie: gdyby archiwum świec przepadło, odtworzenie trzech lat historii dla stu instrumentów z brokera zajmuje — licząc z pomiaru z waszego README — około 27 godzin. I to zakładając, że capital.com ma tyle historii, czego nie ma.

Minimum: nocny pg_dump wysyłany poza maszynę i jedno odtworzenie przetestowane od razu, nie „kiedyś". Kopia leżąca na tym samym dysku nie chroni przed awarią tego dysku.

✗ realny koszt

System operacyjny jest twój

Aktualizacje bezpieczeństwa, restarty po aktualizacji jądra, miejsce na dysku. Większość załatwia unattended-upgrades, ale to ty jesteś tym, kto zauważy, że coś nie wstało.

Raz na kilka lat dochodzi aktualizacja Postgresa do nowej wersji głównej — pg_dump, restore, wieczór pracy.

✗ realny koszt

Nic się samo nie naprawia

Nie ma SLA i nie ma automatycznego przełączenia na zapas. Docker zrestartuje kontener, który padł, ale awarii maszyny nie przeżyjesz bez ręcznej reakcji.

Dla archiwum świec to znośne — przerwa oznacza lukę, którą dociągniesz z brokera. Byłoby nieznośne, gdyby na tym stał automatyczny handel.

Rzecz, którą warto zauważyć

Alertów o tym, że ingest przestał zapisywać świece, nie dostałbyś także w Azure. App Service nie wie, co twoja aplikacja ma robić. Ten monitoring musisz napisać niezależnie od tego, gdzie to stoi — więc nie liczy się jako przewaga chmury.

5. Kolejność prac

  1. Uwierzytelnianie w gatewayu

    Kilkanaście linii w FastAPI: nagłówek z sekretem, sprawdzany globalnie. Pierwsze, bo bez tego reszta nie ma znaczenia — gateway wystawia składanie zleceń i dziś nie pyta o nic.

    To zmiana zachowania, więc idzie przez OpenSpec jako modyfikacja capital-session.

  2. Wyłącz Swaggera w produkcji

    docs_url=None i openapi_url=None, włączane zmienną środowiskową tylko lokalnie. Inaczej podajesz obcemu gotową mapę API razem z endpointami handlowymi.

  3. Dockerfile dla gatewaya i build terminala

    Produkcyjnie, bez --reload. Terminal buduje się do plików statycznych, które serwuje Caddy.

  4. compose.yml

    Cztery usługi. Tylko Caddy ma porty na hoście — reszta żyje w sieci wewnętrznej i jest z zewnątrz nieosiągalna z braku mapowania, a nie dzięki firewallowi.

    Pamiętaj: -p 8010:8010 omija ufw. Jeśli musisz coś opublikować lokalnie, pisz -p 127.0.0.1:8010:8010.

  5. Cloudflare Tunnel + Access

    Kontener cloudflared i polityka „wpuszczaj tylko mój e-mail". Potem zamykasz na VPS-ie wszystkie porty przychodzące, łącznie z 443.

  6. GitHub Actions

    Plik z sekcji 3. Sekrety VPS_HOST i VPS_SSH_KEY w GitHub Secrets.

  7. Kopie zapasowe

    Skrypt, cel poza maszyną, cron, alert przy niepowodzeniu — i pierwsze odtworzenie testowe tego samego dnia.

  8. Watchdog świeżości danych

    Cron co 15 minut sprawdza max(ts) i alarmuje, gdy świece przestały przychodzić. Cicha śmierć ingestu to dziura, której inaczej nie zauważysz tygodniami.

  9. Dopiero teraz moduł market-data

    Na gotowym fundamencie — zamiast dokładać wdrożenie do działającego już ingestu.

6. Kiedy wrócić do chmury

Nie „nigdy". Konkretne sygnały, przy których warto przeliczyć to od nowa:

  • Gdy na tym stanie automatyczny handel. Wtedy przerwa kosztuje pieniądze, a nie tylko lukę w danych — i SLA zaczyna mieć wartość.
  • Gdy pojawi się drugi człowiek. Współdzielone poświadczenia i ręczne wdrożenia przestają się skalować na dwie osoby.
  • Gdy dwa razy z rzędu nie zauważysz awarii przez kilka dni. To znak, że utrzymanie przerosło dostępny czas.
  • Gdy backtesty przestaną się mieścić — ale wtedy potrzebujesz większej maszyny, niekoniecznie chmury.

Migracja na tym etapie jest tania: przy kilku gigabajtach to pg_dump, pg_restore i zmiana adresu w konfiguracji. Godzina pracy. Nie budujesz sobie pułapki — budujesz wersję, którą stać cię utrzymać dzisiaj.
